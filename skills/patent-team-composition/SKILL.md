# 专利团队组成

> **源**：deepseek-harness（dsh）`patent-team-composition`（AGPL 3.0 同源）· 移植日期 2026-08-20 · 本文档为**知识资产**（非角色注册），工具接线标注以 Sati 团队编排层为准。适配注：立场纪律处"方案略起草"为源文件错别字，已微调为"策略起草"。

复杂专利作业优先组建持久团队并行分工；简单案件（单份分析报告、单纯形式补正）直接单会话完成，不必建队。按作业场景选择角色包，**立场配对 + 中立裁判**是复审/无效/诉讼场景的核心结构。

## 前置条件

- 环境提供 `team_*` 工具（Sati 团队编排层 M3 起全量可用：`team_create` / `team_add_member` / `team_create_task` / `team_update_task` / `team_reassign_task` / `team_send_message` / `team_status` / `team_archive`；dsh 的 `agent_teams_*` 工具名在 Sati 侧对应为 `team_*`）；否则回退单会话 + `agent` 工具子代理（`subagent_type`，如 `patent-retriever` / `patent-reviewer`）专家互评。
- 一个 captain（主会话）同时只领导一个活跃团队；建队前确认无未收口的团队。
- 团队成员默认继承 captain 的 LLM 路由与 effort，不指定 provider/model；仅当用户明确要求异构团队（如"检索用 X 模型"）时才传 provider + model。
- 并发闸（**Sati 差异**）：dsh 单团队成员上限 8（插件 `maxMembers` 默认 8）在 Sati 无对应注册上限，改由调度器并发闸约束——`maxConcurrentMembers` 默认 4（deployment 可调），working 成员数达闸限不派新任务（成员邮箱仍投递，pending 任务排队等待空闲成员）；七个场景包成员数（6-7 人）可超过并发闸，按 DAG 依赖逐批分派即可。
- Sati 团队编排层既有事实：M1 落地 durable 成员底座（teams.db 持久化团队/成员/任务/消息，成员为独立持久化会话，sessionKey `team:<teamId>:<memberId>`，主会话任 captain 收口）；M2 落地任务池（状态机 + attempt 计数）与事件驱动调度器（按 DAG 依赖分派 + `maxConcurrentMembers` 并发闸 + 成员邮箱投递）。
- 角色 id 与 M2 协议 roleSlug 自由字符串一致，直接可用；角色注册接线参照 `skills/` 下 `type: role` SKILL.md 惯例（domains 含 "patent" 的检索型角色自动可见）。

## 角色总表

`team_add_member` 的 name 唯一、role 用括号内英文 id：

| 角色 | role id | 立场 | 职责 | 适用场景 |
|---|---|---|---|---|
| 案件管理员 | `case-manager` | 流程中立 | 立案登记与案卷目录、交底书接收、反馈申请人补充资料循环、期限/节点监控（答复期限、复审 3 个月、年费）、补充合格判定收口 | 立案 |
| 检索员 | `researcher` | 中立 | 证据/现有技术检索与核实：公开内容、参数数值、来源可得性；覆盖度评估；可专利性初判 | 全部 |
| 撰写员 | `drafter` | 代理人 | 案件理解（PFE）、文书起草（申请文件/答复稿/补正书/复审请求书/请求书/诉状）、逐特征比对 | 全部 |
| 技术专家 | `technical-expert` | 我方立场 | 技术真实性核验：交底书可实施性、实施例与效果数据、参数合理性；识别夸大/虚构技术陈述 | 立案、撰写、答复、复审、无效、诉讼 |
| 对立审查员 | `adversarial-reviewer` | 审查方 | 授权审查视角红队评审：区别特征认定、技术启示、效果证据、程序表述、法条核验 | 撰写、答复、复审 |
| 申请人代理 | `applicant-counsel` | 申请人方 | 权利要求范围最大化：扩张机会、从权布局、合并修改备选、争辩策略 | 撰写、答复、复审 |
| 形式审查员 | `formal-examiner` | 审查方（初步审查） | 形式缺陷清单核验：文件齐全性、格式规范、附图清晰度、著录项目、签字盖章；补正彻底性判定 | 补正 |
| 无效请求人 | `invalidity-petitioner` | 攻击方 | 无效理由地图（A22.2/22.3/26.3/26.4/33/A9）、证据组合与成功率最大化、预判专利权人应对 | 无效宣告 |
| 专利权人 | `patentee-defender` | 防御/主张 | 无效：质证请求人证据三性、提交反证、修改权利要求缩小范围换维持；诉讼：全面覆盖+等同主张、判赔计算 | 无效宣告、侵权诉讼 |
| 合议组/裁判 | `adjudicator` | 中立裁判 | 程序规则核验（前置审查/口审/庭审/举证期限/证据规则）、双方论点对抗评估、证据采信、结果预判与理由 | 复审、无效宣告、侵权诉讼 |
| 被告代理人 | `defendant-counsel` | 抗辩方 | 不侵权/现有技术抗辩、禁反言与捐献排除等同、提无效反制、豁免抗辩 | 侵权诉讼 |
| 技术调查官 | `tech-investigator` | 中立技术查明 | 实施例/特征比对/等同的技术维度独立判断，与"技术专家"的我方立场区分 | 侵权诉讼（高价值案件可选） |

立场纪律：裁判角色不得参与任一方策略起草（中立性）；技术事实（技术专家/调查官）与法律论证（代理角色/裁判）分离，互不越界；流程节点（期限、送达日、费用）由案件管理员核验，禁止心算。

## 场景角色包与任务 DAG

各场景成员数均不含 captain——captain 为主会话（调度与收口方），不计入成员数。

### 场景一：立案包（4 成员）

成员：案件管理员、检索员、技术专家、撰写员。目标：交底书从接收到"补充合格、可进入撰写"。

| 任务 | 主题 | 负责人 | 依赖 |
|---|---|---|---|
| t1 | 交底书接收与登记：案卷目录、必要文件清单核对 | 案件管理员 | — |
| t2 | 初步检索与可专利性初判：申请类型建议、明显缺陷筛查 | 检索员 | t1 |
| t3 | 交底书质量评估：技术内容清楚度、可实施性、缺失信息清单 | 技术专家 | t2 |
| t4 | 反馈申请人补充资料：补充清单发出与跟踪 | 案件管理员 | t3 |
| t5 | 补充合格判定：补充内容是否满足撰写前条件 | 技术专家 | t4 |
| t6 | 立案收口：立案结论、下一步撰写移交 | captain | t5 |

补充循环纪律：每次反馈须有明确补充清单（问题→依据→期望补充内容），判定不合格时列出剩余缺口后重入 t4，禁止模糊反馈。

### 场景二：撰写包（5 成员）

成员：检索员、撰写员、对立审查员、技术专家、申请人代理。目标：新申请文件（权利要求+说明书+附图要求）。

| 任务 | 主题 | 负责人 | 依赖 |
|---|---|---|---|
| t1 | 交底书理解：PFE 三元组 + 发明点分级 | 撰写员 | — |
| t2 | 现有技术检索：对比文件 + 布局依据 | 检索员 | t1 |
| t3 | 权利要求布局方案（HITL 确认） | 撰写员 | t2 |
| t4 | 说明书五部分撰写 | 撰写员 | t3 |
| t5 | 对立评审：清楚/支持/充分公开/单一性 | 对立审查员 | t4 |
| t6 | 技术核验：实施例/效果数据复核 | 技术专家 | t4（与 t5 并行） |
| t7 | 范围审视：扩张机会与从权布局 | 申请人代理 | t5 |
| t8 | 质量门禁与收口 | captain | t6, t7 |

### 场景三：答复审查意见包（5 成员）

成员：检索员、撰写员、对立审查员、技术专家、申请人代理。撰写团队可直接延续（同成员不重建）。目标：OA 答复。

| 任务 | 主题 | 负责人 | 依赖 |
|---|---|---|---|
| t1 | OA 解析与问题识别（A22.2/22.3/26.3/26.4/33 等） | 撰写员 | — |
| t2 | 法条与审查标准核验 | 对立审查员 | t1 |
| t3 | 修改方案与争辩策略（HITL 确认） | 申请人代理 | t2 |
| t4 | 答复意见书起草 | 撰写员 | t3 |
| t5 | 红队评审交付稿 | 对立审查员 | t4 |
| t6 | 技术核验 | 技术专家 | t4（与 t5 并行） |
| t7 | 收口：答复期限核验 + 提交 | captain | t5, t6 |

### 场景四：补正包（2 成员）

成员：撰写员、形式审查员。目标：补正通知书答复（形式缺陷）或主动补正。

| 任务 | 主题 | 负责人 | 依赖 |
|---|---|---|---|
| t1 | 补正通知书解析：形式缺陷清单 | 形式审查员 | — |
| t2 | 补正书与替换页起草 | 撰写员 | t1 |
| t3 | 缺陷消除核验：逐项对照清单 | 形式审查员 | t2 |
| t4 | 收口：补正期限核验 + 提交 | captain | t3 |

### 场景五：复审包（5 成员）

成员：检索员、撰写员、对立审查员、申请人代理、合议组。目标：驳回决定复审（3 个月期限）。

| 任务 | 主题 | 负责人 | 依赖 |
|---|---|---|---|
| t1 | 驳回决定解析与复审可行性评估（期限/恢复窗口核验） | 申请人代理 | — |
| t2 | 复审请求书与修改方案起草 | 撰写员 | t1 |
| t3 | 请求书评审：争辩强度 + 法条核验 | 对立审查员 | t2 |
| t4 | 前置审查与合议组模拟：撤销/维持推演 + 结果预判 | 合议组 | t3 |
| t5 | 策略收口：复审请求定稿 + HITL 确认 | captain | t4 |

### 场景六：无效宣告包（6 成员）

成员：检索员、撰写员、技术专家、无效请求人、专利权人、合议组。

| 任务 | 主题 | 负责人 | 依赖 |
|---|---|---|---|
| t1 | 案件理解：权利要求拆解 + 无效目标定位 | 撰写员 | — |
| t2 | 证据检索：申请日前公开证据 + 公开日核验 | 检索员 | t1 |
| t3 | 无效理由与证据组合：成功率评估 | 无效请求人 | t2 |
| t4 | 无效请求书/证据清单起草 | 撰写员 | t3 |
| t5 | 专利权人防御预案：质证、反证、修改权利要求方案 | 专利权人 | t3（与 t4 并行） |
| t6 | 合议组裁决模拟：口审推演 + 双方论点对抗评估 + 结果预判 | 合议组 | t4, t5 |
| t7 | 策略收口：对抗结论取舍 + HITL 确认 | captain | t6 |

### 场景七：侵权诉讼包（6–7 成员）

成员：检索员、撰写员、技术专家、专利权人、被告代理人、裁判（+ 技术调查官，高价值案件）。

| 任务 | 主题 | 负责人 | 依赖 |
|---|---|---|---|
| t1 | 权利要求解释与保护范围确定（含禁反言/捐献约束） | 撰写员 | — |
| t2 | 被控物特征分解 + 证据收集（公开渠道/来源验证） | 检索员 | t1 |
| t3 | 侵权比对初判：全面覆盖 + 等同逐项 | 技术专家 | t2 |
| t4 | 原告主张：诉请 + 判赔计算（实际损失/侵权获利/许可费倍数） | 专利权人 | t3 |
| t5 | 被告抗辩：不侵权/现有技术抗辩/禁反言/提无效反制 | 被告代理人 | t3（与 t4 并行） |
| t6 | 庭审对抗模拟：证据采信评估 + 举证责任 + 结果预判 | 裁判 | t4, t5 |
| t7 | 策略收口：对抗结论取舍 + HITL 确认 | captain | t6 |

技术调查官（可选）插入 t3 后：对特征比对/等同判断出中立技术事实意见，交 t6 裁判采信评估。

## 创建序列

1. `team_create`：name 用 `patent-team-<案卷号>`，description 写明案卷、作业类型（立案/撰写/答复/补正/复审/无效/诉讼）与案卷根目录。
2. 按场景角色包依次 `team_add_member`（先中立/通用角色，后对抗双方，最后裁判）。
3. `team_create_task` 按对应场景 DAG 建任务，显式标注 dependencies；调度器自动按依赖分派给空闲成员。
4. 向成员发送角色简报：案卷背景、案卷根目录、必读材料路径、产出落盘路径、立场纪律（本方立场 + 不越界）。

## 协作纪律

- 单一事实源：团队任务状态只是投影，事件日志与案卷产物落盘（`_matter-log.md`）为唯一事实源；成员完成即回报 captain。
- 立场配对：复审/无效 = 请求方（申请人代理/无效请求人）× 防御方（专利权人）+ 合议组（裁判）；诉讼 = 专利权人（原告）× 被告代理人（抗辩）+ 裁判（裁决）+ 调查官（技术查明）。每个立场一个成员，不合并；对抗意见冲突由 captain 收口并说明取舍理由。
- 角色边界：技术专家不评法律论证，代理人/请求人/被告不代写对方文书，裁判不参与任一方策略起草，案件管理员不评技术内容。
- 期限与流程：答复期限、复审 3 个月与恢复窗口、补正期限、送达推定日（+15 日）由案件管理员或 captain 核验，禁止心算。
- HITL 确认点不可跳过：权利要求布局、修改方案、无效理由组合、诉请金额、答复策略在动手前用 `ask_user_question` 确认或至少说明取舍理由。
- 收口：全部任务完成后 `team_archive` 归档团队；归档保留完整成员与任务历史，可随时复查。
