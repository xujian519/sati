# IPC 分类模块：实现现状、官方规则对照与优化建议

> 状态：**分析完成，P0/P1 已实施**（2026-08-07 落地：两级分类精注入 `classifyIpc` 部级 + 高频大类二级匹配 + `queryIpcDetail` 精注入；多重分类并行注入与置信度归一同步上线；P2 消歧 / P3 官方术语对齐未实施）
> 关联模块：`src/knowledge/patent/`（IPC 分类器 / 审查标准加载器 / 专利 MemoryResolver）
> 目标读者：Sati 核心维护者、专利域知识库维护者
> 依据来源：WIPO《国际专利分类斯特拉斯堡协定》、WIPO《国际专利分类使用指南》、CNIPA《专利审查指南》第一部分第四章"专利分类"

---

## 0. TL;DR

- 本项目的"IPC 分类模块"**不是**给专利打官方 IPC 分类号，而是一个**检索路由分类器**：检索时把 query 映射到 IPC 的"部"（A-H），据此决定注入哪个部的审查标准卡片。
- 核心断层：**分类粒度只到"部"，但官方体系、以及本项目自己的审查标准资产，都细化到"大类"（A61/G06/H04…）**。知识库里已有 53 个大类的审查标准、且大类级查询函数已存在，但生产路径只用部级查询，导致一次命中就把整部的混合卡片全注入，噪声大。
- 对照官方规则，还有多重分类被丢弃、置信度归一化偏差、关键词跨部重叠无消歧、功能/应用未区分等问题。
- 建议优先级：**P0 两级分类到"大类"并接通已有的 `queryIpcDetail`**；P1 多重分类注入 + 置信度归一；P2 消歧；P3 对齐官方术语。

## 1. 模块实现现状

### 1.1 模块定位（先厘清它是什么）

IPC 分类在本项目中的唯一职责是**检索路由**，位于专利知识库 `PatentMemoryProvider` 的检索路径上：

```
用户 query
   │
   ├─[1] classifyIpc(query)  ── 关键词匹配，映射到 IPC 部（A-H）
   │         │ 取 top 部，且命中关键词 ≥2 个才继续
   │         ▼
   │    queryIpcStandards(部) ── 注入该部全部审查标准卡片
   │
   ├─[2] 知识图谱检索（关键词 + 可选语义，RRF 融合，可选 rerank）
   └─[3] wiki 卡片联动加载
```

它**不**承担官方意义上的"给专利申请分配 IPC 分类号"。这一点必须明确，否则会错误地要求它实现完整官方分类（见 §4 不建议做的部分）。

### 1.2 关键文件与职责

| 文件 | 职责 |
|---|---|
| `src/knowledge/patent/ipc-classifier.ts` | IPC 部级分类器：A-H 八部关键词表 + 置信度打分 + 排序 |
| `src/knowledge/patent/ipc-standards-loader.ts` | 审查标准卡片加载器：按部 / 按大类 / 按法条 / 关键词四种索引 |
| `src/knowledge/patent/patent-memory-provider.ts` | 专利侧 MemoryResolver，消费分类结果并注入上下文 |
| `src/knowledge/patent/ipc-standards.yaml` | 138 张审查标准卡片数据源（含 `ipcSection` 部 + `ipcDetail` 大类） |
| `assets/patent-rules/patent-ipc-rules.yaml` | 分 IPC 段的审查规则集（规则 id 全是大类级，如 IPC-A61 / IPC-G06） |

### 1.3 分类算法（ipc-classifier.ts）

- **输入**：任意文本（通常是检索 query）。
- **关键词表**：每个部一份手写关键词列表（`IPC_DOMAINS`，A-H 共 8 份），并附 `inventivenessFocus` / `commonKnowledge` 领域要点。
- **打分公式**：

  ```
  ratio      = 命中关键词数 / 该部关键词总数
  confidence = min(0.5 + ratio * 0.5, 1.0)
  ```

  - 有命中才进入结果；按置信度降序返回完整列表。
  - 无命中 → 默认返回 B 部、置信度 0.15。
- **消费门槛**：`patent-memory-provider.ts` 只取 `classification[0]`（top 部），且要求 `matchedKeywords.length >= 2` 才注入，避免单词碰巧命中污染普通对话。
- **高置信度阈值**：`HIGH_CONFIDENCE_THRESHOLD = 0.8`，仅用于可观测性打点（`memory_ipc_classified`）。

### 1.4 审查标准资产的组织粒度

- `ipc-standards.yaml` 中每张卡同时带：
  - `ipcSection`：部级（A-H），共 8 个；
  - `ipcDetail`：大类级（A01/A23/A61/B60/G06/H04…），**共 53 个不同大类**。
- `ipc-standards-loader.ts` 提供四种查询：
  - `queryIpcStandards(部)` → 按 `bySection` 取整部；
  - `queryIpcDetail(大类)` → 按 `ipcDetail` 精确过滤；
  - `queryByArticle(法条)` / `searchStandards(关键词)`。

### 1.5 现状的三个关键事实（决定优化方向）

1. **分类器只输出部级**（`IpcClassification.section` 为 A-H），不产生任何大类信息。
2. **生产路径只调部级查询**：`patent-memory-provider.ts` 用 `queryIpcStandards(top.section)`，一次命中就注入该部**全部**卡片（如命中 A 部 → A61 医药 + A23 食品 + A63 体育等混合注入）。
3. **大类级查询函数 `queryIpcDetail` 已存在，但生产路径未使用**（全仓检索确认只有单元测试引用，属事实上的 dead code）。

## 2. 官方 IPC 分类规则梳理

依据 WIPO《国际专利分类使用指南》与 CNIPA《专利审查指南》第一部分第四章。

### 2.1 法律与版本框架

- 依据《国际专利分类斯特拉斯堡协定》（1971 签订，1975 生效）编制，WIPO 主持修订；英、法文本同等权威，中文为正式译本（有疑义以英/法文为准）。
- 中国 1997 年成为成员国；CNIPA 以最新版 IPC 中文译本为工作文本。
- 改革后改为**每年 1 月 1 日**发布新版本，并区分核心级（core）与高级（advanced）。
- 适用对象：发明专利、实用新型（含已公布申请）；**外观设计不用 IPC**，采用洛迦诺分类。
- 公开文献分类号前加 `Int.Cl.`，括号标注版本年代。

### 2.2 等级结构（分类号编排）

IPC 是五级等级结构，逐级细分：

| 层级 | 名称 | 编号规则 | 示例 |
|---|---|---|---|
| 1 | 部 Section | A-H 共 8 部 | `A` |
| 2 | 大类 Class | 部号 + 两位数字 | `A61` |
| 3 | 小类 Subclass | 大类号 + 一个大写字母 | `A61K` |
| 4 | 大组 Main group | 小类号 + 1~3 位数字 + `/00` | `A61K 36/00` |
| 5 | 小组 Subgroup | `/` 后为除 00 外的数字，层级由类名前圆点数决定 | `A61K 36/28` |

八部：A 人类生活必需 / B 作业·运输 / C 化学·冶金 / D 纺织·造纸 / E 固定建筑物 / F 机械工程·照明·加热·武器·爆破 / G 物理 / H 电学。部内设**分部**（仅信息性标题，无类号）。

分类表内另有**参见（References）**、**附注（Notes）**、**导引标题**界定分类位置范围；附注只适用于相关位置及其细分位置，**与一般规定抵触时附注优先**。

### 2.3 分类核心规则（审查指南第一部分第四章）

**分类的内容**
- **发明信息**：申请全部文本中代表对现有技术贡献的技术信息（新颖、非显而易见），**必须分类，最能代表发明信息的分类号排第一**。
- **附加信息**：不代表贡献但对检索有用的信息（组合物成分、用途特征、引得码），尽可能分类。

**技术主题的确定**
- 类别为**方法 / 产品 / 设备 / 材料**四类（最宽泛含义）。
- 一般以独立权利要求**前序部分**为主、特征部分为限定；前序对象无分类位置时反过来以特征部分为主。
- 权利要求无法确定时，依说明书的技术问题/方案/效果/实施例确定；**说明书中未要求保护但有贡献的内容也要分类**。

**分类方法（五大原则）**
1. **整体分类**：尽可能作为整体分类；但某组成部分本身构成贡献的，再单独分类。
2. **功能分类**：本质属性/功能不受特定应用限制时按功能分（通用阀→F16K；有机化合物→C07）。
3. **应用分类**："专门适用于"某用途、特殊用途、加入更大系统时按应用分（心脏机械阀→A61F 2/24）。
4. **既功能又应用**：两者兼有时双重分类；功能位置缺失只按应用，应用位置缺失只按功能。
5. **多重分类**：涉及不同类型技术主题（产品 + 制备方法）分别分类；另有**多方面分类**、**二级分类表**（A01P/A61P/A61Q/C12S，不能作第一位置分类号）、**引得码**（只能与分类号联合使用）。

**选择分类位置的规则**
- 通用规则：无特殊规则时分入所有合适位置。
- 最先位置规则 / 最后位置规则（由参见、附注指明）。
- 优选位置规则、特殊规则。
- **剩余大组**：找不到充分包括的位置时分入 `99/00`（如 A99Z 99/00）。

**分类步骤**：按部→大类→小类→大组→小组**逐级**分类，直到找到最低等级合适的组。

**特定技术主题专门规则**：化合物→C 部；混合物/组合物按化学组成；制备/处理方法→方法位置；设备/方法互备；专用/通用零件；多步骤方法整体分类；马库什化学通式三步法；组合库→C40B。

**不同公布级的分类强度**：未检索申请从宽（"可能"新颖即分）；已检索审查后从严（确认新颖才分）。

## 3. 实现 vs 官方规则：差距分析

> 前提重申：本模块是检索路由分类器，不需要实现完整官方分类。但它的"精度"直接决定注入哪些审查标准，而这一层恰好与官方规则、以及本项目知识资产的组织方式对不上。

### 🔴 G1 分类粒度只到"部"，官方体系与本项目资产都细化到"大类"（最核心）

- **官方**：五级等级结构；审查指南明确"将申请分配给相应审查部门"靠**精确分类号**而非笼统的部；审查标准本身按大类组织（A61 医药、G06 计算、H04 通信的审查要点完全不同）。
- **现状**：
  - `ipc-standards.yaml` 已有 **53 个大类**的审查标准；`patent-ipc-rules.yaml` 的规则 id 全是大类级（IPC-A61/IPC-G06/IPC-H04…）。
  - 但分类器只输出 8 个部，provider 只调 `queryIpcStandards(部)`。
  - 结果：命中 A 部 → 注入 A 部全部 23 张卡（医药 + 食品 + 体育混杂），噪声大。
  - 更关键：大类级查询 `queryIpcDetail` 已存在，生产路径却未使用（dead code）。
- **影响**：注入上下文与真实技术领域错位，稀释有用信号、浪费 token、误导下游判断。

### 🟠 G2 丢弃"多重分类"

- **官方**：涉及多个技术主题/多方面时应多重分类，目的是检索完备。
- **现状**：`classifyIpc` 返回按置信度排序的完整列表（已有多重分类雏形），但 provider 只取 `classification[0]`。query 同时涉及"医药 + 化学"（A + C）时只注入 top 一部。

### 🟠 G3 置信度公式归一化偏差

- `confidence = 0.5 + 命中数 / 该部关键词总数 * 0.5`。
- 各部关键词数不同（A 部 35 个、D 部 19 个），**同样命中 3 个词，关键词少的部置信度更高**，top 部选择被关键词表大小系统性干扰。
- 违背官方"准确分类"精神。

### 🟡 G4 关键词跨部重叠、无消歧

- "纤维"同时在 C（化学）与 D（纺织）；"结构"放在 E（建筑）但实为泛词；"过滤/分离"在 B 但也常见于医药/化学。
- 官方靠等级结构 + 参见/附注消歧；这里无任何消歧机制，重叠词同时抬高多个部的置信度。

### 🟡 G5 未区分"功能分类 vs 应用分类"

- 关键词表把功能词与应用词混在一起。对部级路由影响有限，但若下沉到大类/小类，这是必须补的概念。当前记为技术债。

### 🟢 G6 次要问题

- **关键词非官方术语**：未对齐官方《IPC 关键词索引》(Catchword Index)，覆盖率靠人工堆砌。
- **默认分类 = B**：无命中硬编码为 B 部，官方对应"剩余位置 99/00 / 不分类"。因 0.15 低置信 + ≥2 门槛不会真的注入，属语义瑕疵而非功能 bug。

## 4. 不建议做的（避免过度工程）

不建议用纯关键词引擎去"实现官方完整 IPC 分类号分配"（部→大类→小类→大组→小组 + 功能/应用 + 引得码）。

官方分类要求**理解技术方案整体**：读权利要求前序 + 特征、说明书、附图，判定功能/应用、做多重分类——这本质是**语义理解任务**，不是关键词匹配能胜任的。对本项目"检索路由"的定位，**做到"部→大类"两级 + 多重选择**就是性价比最高的甜点区。

## 5. 优化建议（按优先级）

| 优先级 | 动作 | 依据的官方规则 | 预期收益 | 涉及文件 |
|---|---|---|---|---|
| **P0** | 两级分类到"大类"，接通已有的 `queryIpcDetail` | 等级结构、按精确分类分配 | 注入噪声大幅下降，盘活 dead code | `ipc-classifier.ts` / `patent-memory-provider.ts` |
| **P1** | 多部/多大类并行注入（多重分类） | 多重分类原则 | 检索完备性 | `patent-memory-provider.ts` |
| **P1** | 置信度归一化（消除关键词表大小偏差） | 准确分类 | top 选择更可靠 | `ipc-classifier.ts` |
| **P2** | 重叠词消歧 / 领域负向词 / 标题加权 | 参见/附注消歧思想 | 减少误路由 | `ipc-classifier.ts` |
| **P3** | 对齐官方关键词索引、功能/应用区分 | 分类原则 | 长期可维护性 | 关键词表 |

### 5.1 P0 实施要点（两级分类到"大类"）

1. **大类关键词来源**：不必人工堆砌，可直接从 `ipc-standards.yaml` 的 53 个 `ipcDetail` 反推——每个大类卡片的 `name` / `keyPoints` / `tips` 里已蕴含领域词；或为高频大类（A61/G06/H04/B60/C07…）补充一份大类级关键词子表。
2. **两级判定**：`classifyIpc` 先定部（现有逻辑），命中后在该部内对候选大类做二次关键词匹配，产出 `detail`（如 `A61`）。
3. **类型扩展**：`IpcClassification` 增加可选 `detail?: string` 与 `detailConfidence?: number`。
4. **注入切换**：`patent-memory-provider.ts` 优先 `queryIpcDetail(detail)`；无 `detail` 或大类命中不足时回退 `queryIpcStandards(section)`，保证向后兼容。
5. **注入上限**：复用现有 `cardLimit`，避免大类卡片过多时上下文膨胀。
6. **测试**：扩展 `tests/knowledge/` 中分类器与注入逻辑用例，覆盖"命中大类→精注入""大类不足→回退部级"两条路径。

### 5.2 P1 实施要点

- **多重分类**：对置信度 ≥ 阈值（如 0.6）或与 top 差距 < 0.1 的部/大类并行注入，而非仅 top-1；仍受总 `cardLimit` 约束。
- **置信度归一**：改用绝对命中数 + 饱和函数（如 `conf = 1 - exp(-hits/k)`），或对各部按关键词表长度归一，消除"小表虚高"。

### 5.3 P2 / P3 实施要点

- **消歧**：给跨部重叠词降权或加领域负向词；标题/独立权利要求关键词加权高于正文。
- **官方术语对齐**：参考官方《IPC 关键词索引》补充与校订关键词，减少人工盲区。
- **功能/应用**：在关键词元数据上标注 `functional` / `applied`，为未来下沉到小类做准备。
