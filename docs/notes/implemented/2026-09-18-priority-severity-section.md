# Agent Note: 「严重级」勾选节与 priority 半自动化（#406）

Status: implemented

## Problem

`priority:` 曾是四个议题维度里**唯一没有自动化**的一个：

| 维度 | 模板字段 | 自动打标 | 门禁 |
|---|---|---|---|
| 类型 | 模板自带 `labels:` | — | 引用必须已声明 |
| 状态 | — | 自动补 `status: triage` | 取值枚举（#337 新增） |
| 优先级 | **无** | **无** | 取值枚举（#337 新增，**只管合法性不管存在性**） |
| 作用域 | 「影响 scope」勾选项 | 自动打 `scope:*` | 双向一致 + 模板间一致 |

后果具体：`docs/technical-debt/README.md` §严重级定义（P0 堵塞 / P1 高 / P2 中 / P3 低）与本仓议题的实际标级之间**没有任何结构耦合**——「定级」这一步可以在全链路被跳过，且无人发现。而技术债恰恰是最需要按级别排期的一类议题。

## Decision

**把「定级」从纯人工变成半自动，与 `scope:` 同构**（三段落地，都在本 PR）：

1. **模板加节**：`.github/ISSUE_TEMPLATE/tech_debt.md` 新增「严重级」节，四个勾选项的文本就是 `docs/technical-debt/README.md` §严重级定义的四行（级别词 + 含义 + 处置）。该表是唯一事实源，模板不另立一套。
2. **分类器加规则**：`scripts/classify-issue.mjs` 解析该节 → `priority: pN`，沿用既有三纪律——**只增不减**、**白名单过滤**（只认 `.github/labels.yml` 声明的 `priority:` 取值）、**不越界读其它节**。
3. **门禁加校验**：`scripts/sync-labels.mjs` 把「影响 scope」与「严重级」两节抽象成一张 `ENUM_SECTIONS` 表，两节共用同一段「模板勾选项 ↔ 带前缀标签双向一致 + 模板之间一致」校验。

三条语义决定（都由测试钉住、都写进规范 §5）：

- **多选取最严重的一档**（`p0` → `p1` → `p2` → `p3`）：§1 规定同一维度至多一个标签，故不能多打；取最严重的理由是**定级宁可保守**（低估严重度比高估危险），且输出是正文的确定函数——同一份正文重复编辑不会抖动。
- **已有 `priority:*` 时不加第二个**：分诊结论优先于模板勾选。这与分类器对 `status:` 的做法同构（"已有状态标签就不补 `triage`"），都是**同一维度的存在性检查**。
- **认不出的级别原样保留**（`P4` / `紧急` 不被静默丢弃）：`normalizeSeverityOption()` 认得出级别前缀时归一为 `p0`–`p3`，认不出时返回清理后的原文。于是门禁能把它报成「模板勾选项「p4 未知档」没有对应的 priority: … 标签声明」，而分类器侧由白名单拦掉——**两侧都不静默**。若按"丢弃"实现，模板里写错的级别会同时绕过门禁与分类器，成为与「模板缺整节」同型的盲区（`TD-PROCGATE-003` 的教训）。

## Alternatives considered

- **把 `priority:` 并入"必须存在"的门禁校验（必勾才放行）** —— 落选。分批分诊的议题（先开、后定级）在 CI 里将无法落地；且门禁无法区分"未定级"与"已定级"，噪声大于收益。半自动的正确形态是"有人勾就自动打，没人勾就仍走人工分诊"。
- **多选时不打标，留给人工分诊** —— 落选。它是"零回归"的保守选择，但等于在最需要兜底的情形（报告者勾了两档 = 拿不准）交回给人工，与"让定级有兜底"的目标相抵；而取最严重既满足维度不变式，又给出确定结果。何况多选通常意味着"至少是这档"，取最严重与语义相符。
- **照 `scope:` 的写法再抄一份校验代码** —— 落选，而且**会踩坑**：`scope:` 标签名是 `scope:ui`（前缀紧接取值），而 `priority:` 标签名是 `priority: p0`（**带一个空格**，与 `status: triage` 同风格）。照抄"前缀 + 取值"的拼接会写出仓库里不存在的标签名。故两节共用一张表，但每节自带 `labelOf()` / `declared()`——这是"同构"在该实现里的准确含义：**同一段逻辑、不同的标签名构造**。
- **给 bug / feature 模板也加「严重级」节** —— 落选（本轮范围）。那需要先想清"模板↔模板"该节的一致性规则（第二节的跨模板比对目前是 no-op，规则已就位）；#406 的验收范围是债务议题这一维。若日后铺开，规则无需再改门禁，只需给模板加节并让选项与 `priority:` 词表一致。
- **让分类器在已有 `priority:*` 时改打勾选那一档（覆盖人工结论）** —— 落选。分类器**只增不减**是它的立身之本（"只做能机械判定的部分"）；要覆盖人工结论就得先删标签，那会让每次 `edited` 都可能改写分诊结果。人工要调整的路径是"先摘标签、再让下一次运行重推"。
- **把「严重级」当作 §1 优先级表的第二份词表（在 `PREFIX_VALUES` 里再加一层映射）** —— 落选。严重级的取值与 `priority:` 取值本就一一对应，多一层映射就是第四份词表；现在由模板↔标签双向校验兜底，与 `scope:` 的处理方式一致。

## Consequences

- **换来**：技术债议题的「定级」从"可以整体跳过"变成**有兜底**——报告者勾一档就自动落 `priority: pN`；`tech_debt.md` 的严重级选项与 `priority:` 词表双向受门禁保护（**实测**：往真模板注入 `- [ ] P4 未知档` ⇒ `pnpm check:issue-labels` 报 `模板勾选项「p4 未知档」没有对应的 priority: p4 未知档 标签声明`；删掉 `P0` 那一行 ⇒ 报 `标签 priority: p0 在 issue 模板的「严重级」节中没有对应勾选项`；两者还原后恢复绿）。
- **规范同步**（同一份语义的多处落点，本轮一并改）：`docs/issue-management.md` §1（优先级"谁来打"改为半自动 + 规则表新增两行）、§2（`tech_debt.md` 的强制信息加入「严重级」）、§5（workflow 表 + 四类标签的可逆性表 + 两条 `priority:` 专属规则）；`docs/technical-debt/README.md` §严重级定义（声明"唯一事实源 + 改表就要改模板"）；`.github/workflows/issue-triage.yml` 头注（`priority:*` 由"摘掉即生效"改为"部分由正文推导"）。
- **`priority:*` 的可逆性变了**，这是本轮最需要记住的行为变化：勾了「严重级」的议题，其 `priority:*` 现在**是正文的投影**——只摘标签会在下一次编辑被加回来，撤销须"取消勾选 + 摘标签"。未勾选（bug / feature / doc 议题、未定级的债务议题）时仍是"摘掉即生效"。§5 的可逆性表已按此改写。
- **付出**：分类器多解析一节（每个新议题多一次 `extractSection`，可忽略）；`sync-labels.mjs` 的校验由"scope 专用"改为表驱动——**现有错误消息逐字未变**（scope 的两条消息仍是 `模板勾选项「x」没有对应的 scope:x 标签声明` / `标签 scope:x 在 issue 模板的「影响 scope」节中没有对应勾选项`），因此既有负控制用例无需改断言，只新增了严重级一族。
- **仍未处理**：`bug_report.md` / `feature_request.md` / `documentation.md` 的议题仍靠人工定级（见 Alternatives 第 4 条）；`stale.yml` 的豁免清单不含 `priority: p0/p1`（`TD-PROCGATE-004`，另一条在账）。
