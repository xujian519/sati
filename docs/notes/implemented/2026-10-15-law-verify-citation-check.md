# Agent Note: 法条引用核验（law_verify）——把「引用的条号是否成立」变成机械判据

Status: implemented

## Problem

Sati 的专利链路能把法条**找出来**（`law_search` 检索引擎，knowledge.db 里的 `law_article` 全文），
但**没有任何判据能判断一条引用是否成立**：文书里写「《专利法》第一百二十条」（专利法只有 82 条）、
「《中华人民共和国专利促进法》」（库里没有这部法）都不会被发现。

上游 dsh 有这一层（`packages/patent/patent-law`，随包索引 + `verifyCitation`），决策词汇
（`valid` / `mismatch` / `out-of-range` / `not-indexed` / `unverified`）已在研究文档里用来描述 Sati 的缺口。
本批把这层补进 Sati，但**索引不照搬**——dsh 用随包资产声明索引，Sati 没有这份资产。

## Decision

**新增 `src/knowledge/legal/{law-index,law-verify,law-verify-tool}.ts`：索引从 knowledge.db 现算，
判定逐条对齐 dsh 的五态，工具 `law_verify` 挂在 `domain: "legal"`。**

**1. 索引从库里现算，选权威源这件事必须留痕。**

`doc_type='law_article'` 里同一部法有多个来源（实测含「专利法」的 10 条：2 条 `source='raw'` 全文 +
8 条 wiki 碎片）。按标题模糊匹配取第一条会把碎片当全文 ⇒ 上界判定崩坏。故：

- 候选按 **归一化法名** 分组，每组取 **`1..N` 连续上界最大者** 为权威源（实测选出专利法 82 条 /
  实施细则 149 条，8 条碎片全部落选）；
- 候选与落选原因一并写进索引（`LawEntry.candidates`）——「选了哪一份」本身是一次判定，不许静默；
- 不按 `source='raw'` 硬编码：前缀只作为报告里的可读标注，判据是「条号连续」这个可验证事实。

**2. 上界只认「连续」，不认「最大」。** `maxContiguousArticle` 从 1 往上一路数，缺号即截断。
实测 `专利实施强制许可办法` 有 44 个条号但最大连续上界只有 43（中间缺一条）——用最大条号会
**把缺号掩盖成合法**。上界为 0（一条都没切出来）时**不给 `out-of-range`**：那是在编造一个
我们并不知道的事实。工具描述与理由文案里把「未收录」与「已收录但未能证明上界」分开写。

**3. 命题判据用条文正文的 n-gram，因为 dsh 依赖的人工词表 Sati 没有。**

dsh 的 `matchProposition` 读 `ArticleEntry.topics`（人工整理的主题词），Sati 侧没有这份词表。
改用「命题与条文正文是否共享任一 3-gram」。实测三种命题对专利法第 22 条：

| 命题 | 共享片段 | 判定 |
|---|---|---|
| 逐字引自该条 | 29 / 29 | `valid` |
| 同义改写（「与在先技术相较…非显而易见性」） | 1 / 17 | `valid`（**弱重合**） |
| 无关但含「创造性」 | 1 / 16 | `valid`（**弱重合**） |
| 与该条毫无共同字 | 0 / 10 | `mismatch` |

结论：判据**无法区分「同义改写」与「碰巧共享一个通用片段」**，而 `mismatch` 是 `block` 级——
按弱重合判 block 会误伤正确引用。故**只在零重合时判 `mismatch`**，并把 `shared/total` 写进理由，
让调用方自己看到「这次通过有多硬」。这是刻意的取舍，不是判据没写完。

**4. 「未核验」不能伪装成「通过」。** 索引不可用时工具**必须**报错退出并显式说明未经核验，
返回里不给任何结构化结论；`source !== 'raw'` 的权威源判 `unverified` 而非 `valid`。
一次静默放行比没有核验更糟（调用方会以为自己已经核过了）。

**5. 域标注：`legal`。**

与 `law_search` 一致（它核验的是法律文本，不是专利数据）。同时给 4 个写作类角色补 `legal` 域——
它们恰恰是「写权利要求/说明书时要核法条引用」的角色，而原 domains 里都没有 `legal`。
⚠️ `patent-electrical-agent` 的 `tools` 是**白名单**（不是 `["*"]`），`scopeToolsForDefinition` 里
白名单与 `visibleDomains` 是**两道独立过滤**，只补域它仍看不到工具——故同时把 `law_verify` 加进其 tools。

## Alternatives considered

- **照搬 dsh 的随包索引（`baseline.ts` + 资产文件）** — 落选。Sati 没有这份资产，且它会与
  knowledge.db 里的法规全文形成**第二份真源**，两者必然漂移；现算索引的唯一真相源就是库。
- **复用 `KnowledgeLawSearch.getById/findByName` 取全文** — 落选（计划原按此设计，实测推翻）。
  那两条语句是 `ORDER BY char_count DESC LIMIT 1`，**只取最大的单个 chunk**；实测专利法全文
  11 318 字分散在 27 条 chunk 里，最大一条仅 498 字。取全文必须自己按 `chunk_index` 拼全部 chunk。
- **用 dsh 的 `matchProposition` 语义（任一 topic 命中即通过）** — 部分落选。语义保留（宽松），
  但词源换成条文正文的 n-gram；同时补上「重合强度」这个 dsh 没有的输出。
- **收紧命题判据（重合率阈值）** — 落选。阈值会把同义改写推进 `mismatch`（`block` 级）误伤正确引用；
  实测 1/17 与 1/16 两类样本无法用阈值分开。选择「透明化」而不是「假装能判」。
- **做《专利审查指南》章节引用核验** — 落选（计划原列，实测形态不成立）。dsh 的指南索引以章节路径
  为键（`第二部分第四章3.2.1.1`），而 Sati 库里指南是 `doc_type='guideline_rule'` 的**规则卡片**
  （标题形如「审查-计算机-根据专利法第25条审查」），没有章节路径体系。硬做只会把「卡片标题存在性」
  伪装成「章节存在性」。工具描述里写明这一边界。
- **支持 `A22.3` 这类审查意见简写** — 落选。该形态没有可靠右边界（`A4纸`、`A22` 都可能误匹配），
  dsh 用负向断言 `(?![0-9A-Za-z\u4e00-\u9fff])` 排除，但 Sati 文书里该简写的使用习惯未经核实，
  宁可不做也不误报。
- **法名匹配用 `title LIKE '%专利法%'`** — 落选。它会同时命中「**专利法实施细则**」（含「专利法」三字），
  而实施细则 149 条 > 专利法 82 条 ⇒ 直接取 maxContig 最大者会**错选**。改为先归一化法名再精确比对。
- **把语料片段当法名（`CLAUDE.md` / `分拆目录` / `第五章 商标相同、近似的审查审理`）** — 落选。
  实测 60 个「法名」里混着这类脏数据，故加「法规后缀白名单」判据（`isLawLikeName`）；
  但**书名号路径不过该判据**——否则编造法名会被静默忽略，而那是比判错更糟的失效模式。

## Consequences

**换来的：**

- 编造条号 / 越界条号 / 未收录法名第一次有了机械判据（`out-of-range` / `not-indexed`），
  且五种 decision 的处置建议（block/warn/allow）随之固定。
- 「上界未能证明」与「未收录」、「法条未切出」三种 `not-indexed` 理由可区分——
  缺的那条不会再伪装成「你引错了」。
- 选了哪一份来源、落选了哪些候选，全部留档在索引里，可复核。
- 命题匹配给出**重合强度**（dsh 没有），把「这次通过有多硬」交回给调用方。

**付出的：**

- **新增工具 ⇒ `toolSchemaDigest` 变 ⇒ llm-replay fixture 必须重录**（本 PR 已重录，
  见下）。这是 A2 相对 A1 的真代价：A1 只改返回值不触发重录，A2 加工具一定触发。
- 索引每次调用现算（实测约 15ms，60 部法 / 96 个文档）——未做缓存，因为缓存的失效逻辑
  比它省下的时间贵。
- 判据宽松这一事实必须靠工具描述与理由文案传达（`valid` 不等于「该条支撑该命题」）；
  描述写长了，但比让用户误信要好。
- 改了 4 个 role skill 的 `domains`（域标注，见 Decision 第 5 点）。

**连带事实一：重录时暴露了 fixture 的既有漂移。**

重录后重放仍失败：fixture 记录的 `model` 是录制时配置里的值，而 `llm-replay-real.spec.ts`
**硬编码** `deepseek-v4-flash`，`~/.sati/sati.yaml` 的 `agent.model` 早已是 `deepseek-flash`。
provider/model 是请求键的一部分 ⇒ 不改这处常量，**这个 fixture 永远无法重录成功**。
已改为与配置同源，并在注释里写明理由（这不是为了迁就新 fixture，而是修一处会持续复发的漂移）。

**连带事实二：录制脚本是追加写，不是覆盖写。**

第一次重录（未清空目录）产出 2 行 `index: 0`，重放报 `duplicate record index 0`。
重录前必须清空 fixture 目录。**这是一个值得单独修的缺陷**（脚本应当拒绝向非空目录写入，
或在写入前清空），本次未改脚本，只在流程上按「先清空」执行。

**验证要点（机检）：** `tests/knowledge/legal/law-verify.spec.ts` 19 用例——纯函数（法名归一化含
剥序号前缀、法规后缀判据、连续上界、引用抽取的重叠消解与编造法名、命题匹配三态）、
判定（假索引覆盖五态 + 「上界未证明不得判 out-of-range」+ 降级不得给结论）、
以及真实知识库的集成断言（专利法 82 / 细则 149、计划里的反例逐条复跑、选源修复回归）。
真实库断言用 `{ skip }` 而非 `return`——本仓库有过「无依赖时 return，于是 CI 上那条永远记为通过」
的先例，那正是「把没跑呈现成通过」。

全量 `pnpm test`：5665 用例中 5659 通过、1 项失败、5 跳过。失败项仍是 `系统 Chrome 存在时可生成 PDF`
（本机 headless Chrome 的既有环境问题，与本批无关）。聚合门禁 `pnpm check` EXIT=0。
