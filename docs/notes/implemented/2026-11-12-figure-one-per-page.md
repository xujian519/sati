# Agent Note: 申请文件附图「每图一页」——渲染链补分页符，判据从 warn 升为 fail

Status: implemented

## Problem

成品核验里有一条图断言 `figure-page-break`：说明书附图节若有 N 张图，就该有 N−1 个**生效**分页符，否则「每图一页」不成立。它此前是 **warn**，理由写在消息里：「当前渲染链不产出分页符 ⇒ 属渲染链能力缺口」。

那个理由在当时成立（母版正文段属性带 `<w:pageBreakBefore w:val="0"/>`，HTML→docx 链确实产不出分页符），但它本身是个坏状态：

1. 「每图一页」是**交付要求**（《专利审查指南》第一部分第一章 4.3 的常见补正理由），把它挂在 warn 上等于把交付要求降级成建议；
2. warn 挡不住交付——两幅图挤在同一页的申请文件照样能定稿；
3. 缺口只要能补，就该先补能力、再把判据升回去，而不是长期停在「已知缺口」。

## Decision

### 一、渲染链在附图节插分页符（分页点落在图与图之间）

- **分页点落在下一幅图所在段落之前**，用 OOXML 的「段前分页」`<w:pageBreakBefore/>`（Word 的「段前分页」），不动段落数量、不加空行。
- **图与它的图号不被拆开**：图号文字按**序号**归属到对应的那幅图（`图2` 归属第 2 幅图）。于是「图在前、图号在后」（`<p><img/></p><p>图1</p>`）与「图号在前、图在后」（`<p>图1</p><p><img/></p>`）两种写法都把图与图号留在同一页：分页点取该图组的**首个**块。
- **节内其它正文段落不被切碎**：不属于图号的文本（说明文字等）归入最近的一幅图，随该图留在同一页。
- 第 1 幅图前不加分页符（附图节本身另起一页），其余每幅图各一个 ⇒ 恰好 N−1 个。
- **计数单位是「幅」不是「段」**：一段里塞两幅图时它们无法被段前分页隔开（拆段会改动版面），这种情况由核验侧如实报「同一段落里，需拆成两段」，不靠硬塞一个破坏体例的实现掩盖。
- **表格单元格里的图不算附图节的一幅图**（它不是一节里的一幅图），渲染侧与核验侧口径一致，不误报。

### 二、分层落点

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 分页点计算 | `docx/renderApplicationDocx.ts`（`markFigurePageBreaks`） | 只对 `drawings` 件生效；按图序算出哪些段落要段前分页 |
| 段属性就位 | `docx/ooxml.ts`（`enablePageBreakBefore`） | 只改 `w:pageBreakBefore` 一项，按 CT_PPr 顺序就位；母版段落的首行缩进/字号/行距/段前段后一律不动 |
| 判据 | `docx/verifyApplicationDocx.ts`（`analyzeFigurePages`） | 读成品 `word/document.xml`，算图数/分页符数/缺分页的图对 |

母版正文段属性里的 `<w:pageBreakBefore w:val="0"/>` 是「显式关闭段前分页」；打开它时是**就地替换**该元素（位置不动），母版没写该元素时才按 CT_PPr 顺序插入。

### 三、判据升级为 fail

- `figure-page-break` 由 **warn 升为 fail**：渲染链现在能产出分页符，「每图一页」是交付要求，不是能力缺口 ⇒ 缺分页就是这份申请文件不合格。
- 消息不再提「渲染链能力缺口」，改为陈述实测值 + **逐对点名**缺分页的图对 + 改法：`说明书附图未做到每图一页：2 张图之间实测 0 个分页符，应为 1 个（第 1 幅图与第 2 幅图之间缺分页符）；修法：在缺分页的那幅图所在段落前设置段前分页（<w:pageBreakBefore/>），使其与前一幅图分属两页`。
- 判据是**两层**：① 总数（N 张图须有 N−1 个生效分页符）；② 位置（第 k 幅图之前必须真的有分页符）。只看总数会漏掉「总数对得上、却有两幅图挤在一页」的情形。
- 缺分页的诊断**按图对点名**，并区分两种不可分的情形：同一段落里的两幅图（段前分页隔不开 → 改法是「拆段」）与普通缺分页（改法是「加段前分页」）。
- 走既有的 `docxError` 通道（`renderPatentDocument.ts` 的结构未动）：fail 级发现进 `docxError`，warn 级发现照旧并入「核验提示」行。

### 四、诚实降级

没有附图节、或附图节只有一幅图时，「每图一页」**无判据可依** ⇒ 不报发现，且 `info.figureChecks.pageBreak` 置 **false**（「未检查」≠「通过」，仓库 AGENTS 第 11 条）。

### 五、图号识别口径唯一事实源

`figureCaptionNumber`（图1 / 图 2 / FIG. 1 / FIG 2）从核验侧提到 `docx/ooxml.ts`，渲染侧（图号归属）与核验侧（图序判据）共用同一个识别口径——两处各写一份必然漂移，漂移会让渲染出的分页点与判据错位。

## Alternatives considered

- **插一个独立的「分页符段落」**（`<w:p><w:r><w:br w:type="page"/></w:r></w:p>`）——段前分页在新页顶部不留空行、也不增加段落数；独立分页段落会在每张图上方留一行空白。
- **用 run 级 `<w:br w:type="page"/>` 塞在图段落开头**——可行，但等于往图段落里塞一个额外 run；段前分页是 OOXML 里表达「本段另起一页」的正规做法，且核验侧早有「显式关闭不算分页」的口径与之配套。
- **改母版：把母版正文段的 `pageBreakBefore w:val="0"` 打开**——那会让**每个**正文段都另起一页。母版体例是唯一事实源，不能为某一个件的排版需求改全局体例。
- **让调用方在 HTML 里自己分页（CSS `page-break-before`）**——HTML→OOXML 链不解析 CSS，且判据读的是成品；把排版责任推给调用方等于把交付要求变成「看运气」。
- **只按总数判（不看位置）**——会漏掉「分页符总数对得上、却断错位置」这种同样不合格的成品。
- **维持 warn**——渲染链已能产出分页符，warn 等于把交付要求继续降级成建议，且 warn 挡不住不合格交付物。
- **只有一幅图时按「通过」报**——违反「未检查 ≠ 通过」；此时如实标 `false`。

## Consequences

- 含两幅以上附图的申请文件现在会因缺分页而**阻断定稿**（`docxError` 通道结构未动，只多了它的一个来源）。
- 段前分页只改 `w:pageBreakBefore` 一项：母版段落的首行缩进（`w:ind w:firstLine="0"`）、字号（`w:sz w:val="24"`）、行距（`w:spacing w:line="360"`）等在端到端断言里逐条守着。
- **零 `inputSchema` 变更、零新增 builtin 工具** ⇒ 不触发 llm-replay fixture 重录（AGENTS 第 6 条）。
- 图号识别口径换了归属文件（`verifyApplicationDocx.ts` → `ooxml.ts`），两处调用方同步改，行为不变。

## Verification

- `pnpm exec tsc --noEmit`：零错误；`pnpm build`：通过。
- `node --test dist/tests/patent/document/*.spec.js`：全绿（除 `renderPatentDocument.spec.ts` 的「系统 Chrome 存在时可生成 PDF」——本机沙箱下 Chrome 无头不可用，属既有的环境性失败，与本改动无关）。
- 端到端探针（`render_patent_document` → JSZip 读 `word/document.xml`）：两幅附图之间**恰有 1 个生效分页符**，分页符落在第 2 幅图的段落上（`<w:pageBreakBefore/>` 与母版 `<w:pageBreakBefore w:val="0"/>` 同位置，其余段属性逐条相同），图号段无分页符 ⇒ 图与图号同页；核验 `figureChecks.pageBreak=true`、无 `figure-page-break` 发现、`passed=true`。
- 真机复核（LibreOffice headless 转 PDF）：成品 6 页，附图节占 2 页——第 5 页「说明书附图 / 图1」、第 6 页「说明书附图 / 图2」，即**每图一页**且图与图号同页。

## 遗留（如实留记，不在本批范围）

- 探针顺带发现一处**既有**（非本批引入）的误报：「图与图号写在同一段」时，内容落地判据 `parts-nonempty` 会报「文本未落地」——因为 `statElement` 把含图的段落只计为图、不计段。属既有内容判据的边界，本批未改（改了会动到既有产物的其它部分），单独留记待议。
