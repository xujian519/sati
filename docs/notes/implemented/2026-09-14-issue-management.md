# Agent Note: 议题治理——标签即状态，结论必须落地

Status: implemented

## Problem

项目的规范体系此前只覆盖"代码怎么进仓库"：`docs/development-standards.md` 管门禁，`docs/notes/` 管决策。而**问题怎么进来**这一侧是空白的——只有 3 个 issue 模板和一道 PR 追溯门禁。

缺口是具体的：议题没有状态体系（无法回答"哪些还没分诊""哪些在处理中"），模板里已经结构化的「影响 scope」勾选是死的（没人能用它筛选），关闭议题没有留下结论的纪律（"修好了"和"不修"都只点一下 Close），长期无活动的议题无人清理。

结果是议题沦为留言板：能被读到，但不能被检索、不能被统计、关闭后不产生知识。

## Decision

建立议题治理的完整链路，遵循项目既有的"陈述 + 机器门禁 + 决策记录"三件套：

**标签即状态**。`.github/labels.yml` 是标签体系的单一事实源，四个维度：类型（`bug`/`enhancement`/…）、状态（`status: triage|in-progress|blocked`）、优先级（`priority: p0..p3`）、作用域（`scope:*`，与提交 scope 同名）。终态由**关闭**表达，不设 `status: done`——避免"标签说完成、议题还开着"的双写。

**机器门禁**（`scripts/sync-labels.mjs --check`，挂 `pnpm lint`）双向校验清单与 issue 模板：模板 `labels:` 引用的标签必须已声明，模板「影响 scope」勾选项与 `scope:*` 标签集合必须一一对应。任一方向漂移即红。清单自身也校验（名唯一、color 为 6 位 hex、描述 ≤100 字符）。

**自动分类**（`scripts/classify-issue.mjs` + `.github/workflows/issue-triage.yml`）把模板里的人工勾选翻译成 `scope:*` 标签，并给无状态标签的新议题补 `status: triage`。只增不减——误判由人工摘除，脚本不会打回（`status:` 例外：全摘光会回弹到待分诊，这是刻意的）。

**分诊节奏不承诺 SLA**：新议题默认落 `status: triage`，维护者批量过一遍。不写"48 小时响应"——单人项目承诺做不到的时效比不承诺更伤贡献者。

**关闭纪律**：关闭议题必须留一句结论（根本原因 / 为什么不做），设计使然的取舍落成 `docs/notes/` 决策记录。议题是决策的讨论现场，note 才是决策的家。

**过期治理**（`stale.yml`）：90 天无活动标 `stale`，再 30 天关闭；已排期（有 milestone）与已认领（`in-progress`/`blocked`/`help wanted`/`good first issue`/`pinned`）一律豁免。

明细层规范见 `docs/issue-management.md`。

## Alternatives considered

- **引入 CODEOWNERS + 自动指派** — 落选。CODEOWNERS 的核心价值是"把 review 路由给正确的人"，而本项目是单人维护，自动指派只能指派给维护者自己，产出为零成本非零的配置。等出现第二位稳定维护者、或模块 owner 真的分化（如 `patent/` 与 `ui/` 由不同人负责）时再引入，届时它同时能驱动 review 请求与关键路径保护。
- **用 GitHub Projects 看板管理状态** — 落选。状态已由 `status:*` 标签完整表达，按标签筛选的议题列表**就是**看板列；引入 Projects 会制造标签与卡片两套状态，需要人工同步且必然漂移。看板的增量价值（拖拽、自定义字段）在本项目规模下不值得这份同步成本。
- **用官方 `actions/labeler` 自动打标签** — 落选。它按 PR 改动的文件路径打标签，只覆盖 PR；本规范要解决的是 issue 侧"模板勾选变成死数据"，语义来源是模板的「影响 scope」节而非文件路径，需要自定义解析。两者不冲突——若将来想给 PR 也加路径标签，`labeler` 仍可补位。
- **把标签直接硬编码在脚本与 workflow 里** — 落选。这正是要避免的漂移源：模板、脚本、仓库设置三处各写一份标签名，改一处就静默失效。改为清单声明 + 门禁双向校验，让漂移在 lint 阶段就红——事实上本门禁在落地当天就抓出了清单里两个真实的 YAML 陷阱（`008672` 被解析为数字 8672、`6e7781` 被解析为科学计数法 Infinity），证明了"门禁真的在拦"。
- **关闭议题时强制校验结论字数** — 落选。理论上可以加一个"关闭时 body 长度不足则拒绝"的 Action，但那会把"写一句真诚的结论"变成"凑够字数"，生产的是填充文字而非知识。此类规则的可靠性来自维护习惯与 review，不来自校验器；把它伪装成门禁只会败坏门禁的可信度。规范里明确标注它是**人工约定**。
- **stale 阈值收紧到 30 天标记 / 14 天关闭** — 落选。项目规模小、议题总量少，误关一个真实议题的代价远高于多留几个静默议题；且自动关闭会连带冻结"重新打开"这条路径之外的上下文语境。90+30 是"默认归档"而非"判决"，配套的关闭文案明确写出"评论即可 reopen"。
- **不做 stale，纯手工治理** — 落选。单人维护下"我会定期清理"这类承诺缺乏外部提醒机制，必然落空；而 stale bot 的价值恰恰在于它是唯一不依赖自律的治理环节。

## Consequences

**换来**：议题首次可被筛选与统计（按 scope 找"专利相关有哪些"、按 status 看"待分诊队列"）；模板里原本死掉的勾选成为结构化数据；标签漂移在 lint 阶段而非"发现筛选结果不对"时暴露；关闭议题产生可搜索的结论，而非需要重读整条讨论串；长期无活动的议题有确定归宿。

**付出**：lint 链变长一道门禁，新增 2 个脚本、2 个 workflow、2 个测试文件；标签实体同步是**手工步骤**（CI 无仓库设置写权限），存在"清单已改、仓库未同步"的窗口——此时自动分类会因标签不存在而失败，失败是可见的（workflow 报错）而非静默，这是刻意的选择：宁可红，不可静默失效。`status: triage` 的回弹行为需要维护者理解——人工把状态标签全摘光会被重新补上。

**未覆盖**：CODEOWNERS、Projects 看板、GitHub Discussions 分流、里程碑的自动化创建——前两项理由见上，后两项在项目规模变化前不引入。
