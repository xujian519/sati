# Agent Note: 说明书章节识别接受提交格式的纯文本标题

Status: implemented

## Problem

`validate_specification` 的必需章节只用 `/^#{1,3}\s*技术领域/m` 这类 Markdown 标题正则识别。CNIPA 提交格式的标准说明书是纯文本标题，于是完整说明书被判「技术领域、背景技术、发明内容、附图说明、具体实施方式」五节全缺、`score` 降到 0.4。附图说明正文提取同样只认 `#`，图文标号核验也跟着失效。

## Decision

抽出 `matchSectionHeading(line)` 与统一正则，按整行识别：Markdown `#`–`######`、纯文本、编号（`一、` / `1.` / `（一）`）、方括号（`【技术领域】`）、行首行尾空白与行尾冒号。章节存在性检查与附图说明正文提取共用同一识别函数，避免两套正则再次漂移。正文中出现章节名（如「本发明属于技术领域」）不算标题。

## Alternatives considered

- **只改必需章节、不改附图说明提取** — 结构检查会通过，但图文标号核验仍拿不到纯文本章节正文，形成半修。
- **识别任意包含章节名的行** — 正文提及「技术领域」会被当成标题，产生假通过；必须保持整行匹配。
- **先把纯文本说明书规范化成 Markdown 再校验** — 需要改写入参或临时文本，且无法可靠区分标题与正文，副作用大于收益。
- **只接受纯文本、放弃 Markdown** — 现有草稿与测试都使用 Markdown，会造成向后不兼容。

## Consequences

标准提交格式的纯文本说明书可通过结构检查，Markdown 草稿行为不变。标题识别更宽松后，形如 `1. 技术领域` 的列表行也会被视为标题——这是提交格式的常见形态，接受该取舍。工具顶层描述补充了支持的标题格式；`inputSchema` 未变，不需要重录 llm-replay。
