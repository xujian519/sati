# Agent Note: 分层规则包的缓存失效判据改为内容指纹

Status: implemented

## Problem

`rule_check(scope:"pack")` 对分层规则包（`rules/base` + `rules/domains/*` + 项目 overrides）
的结果做进程内缓存，而缓存键只覆盖**顶层清单 `.sati/rules.yaml` 的 mtime**。

分层包的实际内容由各层**规则文件**决定，清单只是"声明装配了哪些层"。于是「改了
`rules/base/*.yaml` 或某个 domain 的规则文件、而没动清单」这个最普通的编辑路径**不会**让
缓存失效：Sati 的主形态是长驻进程（gateway / desktop），用户改完规则后 `rule_check` 继续按
旧规则作答，且没有任何信号——**该拦的没拦、已废弃的还在拦**（规则引擎承载合规约束，
`action: block` 可经 policy-bridge 拦截工具调用，所以这不是"输出有点旧"而是"合规面失真"）。

短命进程（CLI 一次性调用）不受影响，这正是它长期没被发现的原因。

## Decision

`src/rule/runtime/rule-pack.ts` 新增 `computeRulePackFingerprint()`，`rule_check` 的 pack
缓存键改调该函数。指纹 = 清单（路径 + **解析结果**）+ 各已装载层规则文件的
`(文件名, mtimeMs)` 有序集合。

三条实现要点各自对应一个已识别的失败模式：

1. **先按清单展开层，再枚举各层目录**。展开逻辑与 `loadRulePack` 的加载逻辑抽成同一份
   `resolveLayerRefs()`——两处各写一份，迟早会让指纹指向一组并未参与加载的目录（"缓存键
   看起来覆盖了、实际没有"）。
2. **每次调用重新枚举目录，而不是复用上一次加载的 `sources`**。复用会导致**新增文件**永远
   进不了摘要（新文件不在上次的 sources 里，其 mtime 无处可记）——这正是"沿最自然的写法
   走一步就会掉进的坑"。
3. **不哈希整个 `rules/` 目录**（也不按目录 mtime 折中）。清单声明了哪些层参与加载，未声明
   目录的内容与加载结果无关；纳入会让指纹在无关文件变动时空转重载版本化资产。

清单部分用**解析结果**（`JSON.stringify(manifest)`）而不是清单 mtime：mtime 变而内容没变
（touch / 重新 checkout 等价内容）不该空转重载；内容变则必须失效，与 mtime 是否变动无关。

`computeRulePackFingerprint` 是**全函数**：清单/目录/文件的读取失败都在内部降级为占位符
（`absent` / `unparsable` / `missing` / `unreadable` / `?`），不抛错。因此调用方**不设**
"算不出来就用旧缓存"的兜底——那会把本缺陷（静默陈旧）原样请回来；宁可让异常冒出去变成
一次可见的失败。

## Alternatives considered

- **按 issue 原文只做「清单 mtime + 上次加载的 sources 的 mtime 集合」** — 落选：`sources`
  是**上一次加载**的产物，新增的层规则文件不在其中，其 mtime 永远进不了摘要 ⇒ 遗留一个
  与母缺陷同型的"新增文件不生效"漏洞。issue 自己也在"额外信息"里点了这个风险，但"mtime
  集合"这个措辞仍会把人引到 sources 上；改成每次重新枚举目录才能同时覆盖「原地修改」与
  「增删文件」。
- **递归哈希整个 `rules/` 目录** — 落选：清单的语义就是"哪些层参与"，未声明目录（例如装了
  但没启用的 domain 包）的改动与加载结果无关，纳入后会每次空转重载。用一条用例把这个边界
  钉住了（`computeRulePackFingerprint 只看清单声明的层`）。
- **按目录 mtime（issue 给的折中方案）** — 落选：目录 mtime 只在增删文件时变，**不覆盖原地
  修改**——而"改规则内容"恰恰是本 issue 的主场景。折中方案解决不了主场景，还要额外解释
  "为什么改了规则没生效、加个文件反而生效"。
- **对文件做内容哈希（摘要算法）而非 mtime** — 落选：每次调用都要读全部规则文件的字节，
  而 mtime 只需 `statSync`。规则文件数量本身不多，但"每次 rule_check 都读一遍盘"与
  "缓存本来就是为了避免重复读盘"直接冲突；mtimeMs 的毫秒粒度对人工编辑足够。
- **用文件系统监听（`fs.watch`）在变更时主动失效** — 落选：监听器要在工具工厂里持有生命
  周期与清理责任（长驻进程、多工作区、监听失效的静默降级），而"调用时比对指纹"是无状态的
  一次性判断。为一个 `S` 级债务引入需要自己维护的后台机制不成比例。
- **只在文档里把"缓存按清单 mtime 失效"写清楚，不改代码** — 落选：`rules/README.md` 原本
  就是这么写的（"缓存按清单 mtime 失效"），文档是准确的、行为是错的——这是**缺陷**不是
  文档缺口。（顺带：该行已随本次修订更新，因为口径变了。）
- **顺手把 `manifestMtimeMs` 字段删掉（认为被指纹取代）** — 落选：它是 `RulePackLoadResult`
  的公开面，有测试与消费方读它；本次只改"用什么做失效判断"，不动结果结构（避免不必要的
  契约面变化）。

## Consequences

- **换来**：改任意层规则文件（原地改 / 新增 / 删除）都会在下次 `rule_check(pack)` 被检出并按
  新规则评估；缓存仍然有效（内容未变时指纹稳定，不空转重载）。
- **付出**：每次 `scope=pack` 调用多一轮 `readdirSync + statSync`（清单 1 个 + 各层若干文件，
  内置 base 4 个、每 domain 数个）。这条路径不是热路径，而"陈旧合规规则"的代价是合规面失真，
  取舍明确。
- **仍未覆盖**：mtimeMs 粒度内（同一毫秒）连续两次改写会被判为未变；指纹不跨进程共享（每个
  长驻进程各自判定，这本来就是缓存的边界）。
- **残余缺口**（登记台账）：指纹只覆盖**规则内容**，不覆盖 `overrides` 目录本身的**存在性
  变化**之外的清单语义变化（例如把 base 从内置名改成等价路径——指纹会变，行为不变，属空转
  重载，方向无害）。
