# Agent Note: V4 附图标记名称归一化（括号形与裸数字形视为同一组成部分）

Status: implemented

## Problem

V4（细则第 21 条：表示同一组成部分的附图标记应当一致）比较的是**名称字面**，而
`stripRefMark` 只剥离括号式标记：

```
stripRefMark("处理模块(20)") = "处理模块"
stripRefMark("处理模块20")   = "处理模块20"   ← 与上一行不同名
```

同一组件在附图里写 `处理模块(20)`、在另一幅图或另一处写 `处理模块20` 即判 **V4 fail**
（附图不得定稿）。而本项目自有知识库卡片（`knowledge.db` doc `255359a2208c6957`）明确
说明书正文的惯例是"名称+数字、不加括号"，图面惯例才是括号形——两种写法**并存是常态**，
于是这条硬门禁会稳定地产出假阳性，把"书写形态差异"报成"同一标记指两个部件"。

## Decision

新增纯函数 `normalizeRefLabel(label)`：`stripRefMark` 之后再去掉尾部裸数字（`\s*\d{1,3}\s*$`）
并 `trim`；V4 的名称比较改用它。**归一化只影响比较，不影响呈现**——`stripRefMark` 保持原样
（`brief.ts` 的附图说明草稿依赖其输出格式），渲染输出的标签文本也不变。

## Alternatives considered

- **改 `stripRefMark` 本身（让它也剥裸数字）** — 落选：`stripRefMark` 是"呈现形态"的剥离器，
  简报/附图说明直接用它的输出拼"处理模块"；在那里剥数字会让"名称+数字"的正文惯例在简报里
  被吞掉尾数字，属于用一个错误的呈现换一个正确的比较。
- **在 V4 比较处就地写正则（不提取纯函数）** — 落选：归一化规则需要被表驱动测试逐形态钉住
  （括号/全角括号/裸数字/带空白/多行首行），也需要被 P1-4 的 `extractClaimRefs` 复用同一词法；
  散在比较循环里的正则没有这两个性质。
- **把 V4 降级为 warn（"可能是同一部件"）** — 落选：V4 是硬门禁的价值在于"同一标记两个部件"
  是实质性缺陷（会导致说明书指代错误），降级等于放弃这条规则；真正要修的是它的比较口径。
- **在渲染侧统一标签写法（强制"名称(N)"）** — 落选：渲染器不该改写作者给的标签文本
  （label 是模型/代理师写的内容，改写等于静默修改交付物）；且说明书正文的写法不受渲染器控制，
  统一渲染也消除不了两种形态并存。
- **归一化时也剥离后缀字母/罗马数字（如 "处理模块A"）** — 落选（本次不做）：`20a` 形式的
  标记在本项目数据里未出现，且剥离字母会误伤名称本身带字母的部件（"USB接口"）；先只处理
  已被实测证实的两种形态。

## Consequences

**换来**：V4 不再因标注书写形态差异误报；归一化成为"名称比较"的唯一口径，为后续
`extractClaimRefs`（P1-4）提供共用词法。

**付出**：

- 极端情况下会**放过**一类冲突：同一标记在一处写 `处理模块20`、另一处写 `处理模块 20`
  （带空格）被视为一致——这正是意图。
- 若某部件名本身以数字结尾且数字不同于标记（如 `2010`），归一化会把它当标记剥掉：
  名称比较退化为前缀比较。附图标签以"名称+标记"为惯例，该退化的代价低于假阳性；
  如将来出现真实案例，应改为"剥离与 node.ref 相符的尾数字"（需要 ref 参与，本次未做）。
