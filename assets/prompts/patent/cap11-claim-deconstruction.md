# CAP11 权利要求四层解析（W-10 claim-deconstructor）

## 目标

对专利权利要求进行系统化分解，输出结构化技术特征清单，为 CAP02 技术对比分析和下游 provision worker 提供精确的"特征颗粒度"输入。

## 核心方法：最小技术单元法（MTU）

将权利要求逐句分解为不可再分的技术单元。每个 MTU 必须同时满足：
1. **单一技术手段**——不包含两个独立的技术动作
2. **单一技术效果**——在权利要求中起到一个独立的技术作用
3. **可对比性**——在现有技术中可以找到或推断对应的技术特征

## 四层解析框架

对每个 MTU，从四个递进层次进行标注：

### L1 词法层（Lexical）
- 字面表达：连接词（其特征在于、包括、进一步包括）、限定词（所述、至少一个）、数值范围
- 位置关系：位于 A 与 B 之间、固定于 C 上、与 D 连接
- 语法角色：主语（执行主体）、谓语（动作/手段）、宾语（作用对象）、状语（条件/方式/位置）

### L2 语义层（Semantic）
- 技术含义：该术语在所属技术领域中的公认含义
- 功能性限定：是否使用了功能性语言（如"用于……的装置"）
- 方法/产品：属于方法特征还是产品特征
- 上位/下位：该特征在本领域的上位/下位概念范围

### L3 功能层（Functional）
- 技术作用：该特征在发明中实现的**独立技术作用**
- 协同关系：该特征与其他 MTU 之间的功能协同（A 使 B 能够……、C 为 D 提供……）
- 必要/非必要：从要解决的技术问题判断该特征是否为必要技术特征

### L4 效果层（Effect）
- 技术效果：该特征直接带来的可验证技术效果（区别于说明书中的"有益效果"概括）
- 效果链：从该特征出发的技术效果因果链（特征→直接效果→间接效果→发明目的）
- 数值/实验：是否有实验结果、对比例、数值范围支持该效果

## 步骤

### Step 1：权利要求结构分解

1. 识别独立权利要求和从属权利要求
2. 分解独立权利要求的前序部分和特征部分
3. 按"最小技术单元"切分每个技术特征

### Step 2：四层标注

对每个 MTU，按 L1→L2→L3→L4 逐层标注：

```
MTU-1: [字面文本]
  L1 (词法): 主语=[], 谓语=[], 宾语=[], 状语=[], 连接词=[]
  L2 (语义): 技术含义=[], 限定类型=[字面/功能/方法/参数], 上位概念=[]
  L3 (功能): 技术作用=[], 协同=[MTU-2:提供前提], 必要性=[必要/非必要]
  L4 (效果): 直接效果=[], 间接效果=[], 效果链=[MTU-1 → 效果A → MTU-3增强]
```

### Step 3：特征分类

对标注完的 MTU 进行分类：
- **结构特征**：装置/组件/连接关系
- **方法/步骤特征**：工艺/流程/使用步骤
- **参数/数值特征**：温度/压力/比例/尺寸
- **功能性限定特征**：以功能限定的结构
- **材料/组分特征**：化学/材料/配方

### Step 4：输出结构化特征清单

```yaml
claim_deconstruction:
  claim_index: 1
  claim_type: independent
  mtus:
    - id: MTU-1
      text: "..."
      layers:
        lexical: { subject: "...", predicate: "...", object: "...", adverbial: "..." }
        semantic: { meaning: "...", limitation_type: "字面|功能|方法|参数", hypernym: "..." }
        functional: { role: "...", synergy_with: ["MTU-2"], essential: true }
        effect: { direct: "...", indirect: "...", chain: "..." }
      feature_type: 结构特征|方法特征|参数特征|功能性限定|材料特征
  total_mtus: N
```

## 输出

- `outputs/claim-deconstruction-{claimIndex}.yaml` — 结构化特征清单（供 CAP02 和下游 provision 直接消费）
- `outputs/claim-deconstruction-report.md` — 人类可读解析报告

## 与上下游的关系

- **上游**：`converted/权利要求.txt` 或用户直接提供的权利要求文本
- **下游**：CAP02 (W-03) 直接消费 `claim-deconstruction-*.yaml` 的 MTU 清单作为对比颗粒度
- **与 P-B01 的区别**：P-B01 是侵权场景的权利要求解释（确定保护范围），本 worker 是技术特征分解（确定对比颗粒度）

## 约束

- 不得跳过 L1 直接做 L3/L4——四层必须逐层递进
- MTU 颗粒度必须基于"不可再分"原则，不可为了简化分析而合并
- 不得编造特征的技术含义——不确定时标注 **[待确认]** 并说明推测依据
- 一个 MTU 只能标注一个 direct effect——避免效果混淆
